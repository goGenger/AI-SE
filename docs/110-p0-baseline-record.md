### 7.1 三问的答案

**（a）失败发生在 8 个规划阶段中的哪一个？**（按最后到达的阶段）

| 夹具               | 最后到达阶段                        | 说明                                                                                                                           |
| ------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| L1（第 1 次）      | `architecture`（第 4 阶段）         | requirement_analysis 58s + functional_spec 89s + technical_spec 15s 后撞线                                                     |
| **L1（第 2 次）**  | **全部 8 阶段通过**                 | 同一个需求、同一天，**150s 走完并 `PLANNING_COMPLETED`** —— 同一需求「一次超时、一次通过」                                     |
| L2                 | `functional_spec`（第 2 阶段）      | requirement_analysis 单阶段耗时异常（事件跨度 >900s）                                                                          |
| **S2（全新规划）** | `architecture`（第 4 阶段）         | **单个阶段 technical_spec 耗时 120s**（07:44:42→07:46:42），第 4 阶段开始时预算已耗尽                                          |
| S3（全新规划）     | 运行中                              | 同上，待观察                                                                                                                   |
| M1                 | `ui_spec`（第 7 阶段）              | 前 6 阶段全部成功                                                                                                              |
| M2                 | `ui_spec`（第 7 阶段）              | 同上                                                                                                                           |
| M3                 | `requirement_analysis`（第 1 阶段） | 运行报 `TIMEOUT_ERROR`，但其阶段事件 13s 即失败；另叠加 harness 侧对平台 API 的一次 `fetch failed`（网络瞬时错误，与规划无关） |
| S1                 | 全部 8 阶段通过                     | 106s                                                                                                                           |

**（b）是超时，还是别的错误（如 JSON 校验反复失败）？**
全部 6 次失败的 run 错误码均为 **`TIMEOUT_ERROR`**（`This operation was aborted`）；事件流中**没有** `PLANNING_SCHEMA_VALIDATION_FAILED` / `PLANNING_REPAIR_REQUESTED`——即**不是**结构化输出校验反复失败，而是**墙钟超时**。唯一例外是 M3 叠加的 harness 侧 `fetch failed`（平台 API 的一次瞬时不可达）。

**（c）180s 是单阶段上限还是整个规划的总上限？**
**是整个规划运行的总上限。** `PLANNING_TIMEOUT_MS = 180_000`（`apps/server/src/services/planningService.ts:36`，**硬编码、无环境变量**）同时作为 `PlanningAgent` 的 `defaultTimeoutMs` 与本次 `run` 的 `timeoutMs` 传入，即 8 个阶段共用同一个 180s 墙钟预算；**各阶段没有独立上限**（证据：L1 的 3 个阶段耗时合计 162s，第 4 阶段开始时已近预算末端）。

### 7.2 影响与建议

- 影响：**不是 L/M 档特有**——S2（S 档最小夹具）的全新规划同样 180s 超时；且**同一需求成败不稳定**（L1 的 fail→pass 说明余量太小）；失败后需求状态变 `FAILED`，需重新 analyze。
- 关键机制：预算被**个别慢阶段**吃掉——实测单阶段 89s（L1 functional_spec）、120s（S2 technical_spec）都出现过；阶段耗时波动是主因，不是总任务量。
- 对加固计划：直接对应 **T5（规划阶段度量与精简）**——度量项应包含「每阶段耗时分布 / 触顶阶段 / 同一需求重复规划的成功率」；**T6（工作流级预算）** 可顺带覆盖「规划预算可配置」。
- 本阶段**未改动平台代码**（P0 范围：不改生产代码），仅如实记录。
