## 5. 补齐的前置任务：N0 = E1 夹具建设（阶段 B 最前）

**问题**：v2 的验收场景（§2）、阶段 B 出口基线、阶段 C 出口对比、阶段 E 全部以 `E1-taskboard-prd.md` 为输入，但该文件、隐藏 oracle、oracle 自检**均不存在**（§2 行 9）。没有 N0，阶段 B 出口就无从跑起。

**范围**

1. **E1 PRD 正文**：TaskBoard 项目需求，含 9 个 FR、30 条 AC（每条带编号、文本、Must/Should、验证方式、是否 smoke）；规则要写到「可被确定性 oracle 判定」的粒度（`title` 长度、`dueDate` 合法性、用户名大小写、数据隔离、`/healthz`、`data-testid` 等）。
2. **隐藏 oracle**：独立 Node 黑盒脚本（`fetch`），按 v2 附录 A 的类别表实现；**不得进入工作区、不得进入提示词、不得由被测 Agent 编写**（沿用 `docs/109` §架构判定 5 的隔离约定）。
3. **oracle 自检（必须做）**：对一份人工审核的**参考实现**运行（Must 全通过）+ 对 **5–6 个变异版本**运行（必须全部检出）。P0 已证明该模式有效——`docs/110` §3 的 oracle 自检抓出了参考解自身的 bug。
4. **可构建性验证**：E1 要求真实构建与容器部署，需先确认平台能在夹具工作区完成真实构建（对照 §8 风险 1）。

**验收**：oracle 对参考实现全 Must 通过；5–6 个变异版本全部被检出；PRD 的 30 条 AC 与 oracle 的断言一一对应（无孤立断言）。
