## 架构判定（默认已定，可逐条否决）

1. **驱动方式**：只经 REST（复用 `packages/eval` 的 CLI 与 harness），**不直连数据库**、不调用内部函数构造状态。
2. **清理方式**：`DELETE /api/projects/:id`（级联），与 harness `--cleanup` 同一条路径；不用 SQL 直删。
3. **临时基线口径（冻结）**：S 档 = S1/S2/S3 各 1 次，**同一次运行产物**（不混用历史样本）；S2 未取得则记为 `未取得（规划失败：92df0d15…）`。**本阶段产物不构成噪声线**，不得表述为「基线补齐」。
4. **决策点（默认值，可否决）**：
   - **(a) 重跑范围**：默认**整批** `--fixtures S1,S2,S3 --runs 1`（S1/S3 复用计划仅重跑执行，S2 触发重新 analyze）。理由：一次产出的样本口径统一，避免跨 harness 版本混样本。备选（更省 token）：只跑 `--fixtures S2`，S1/S3 复用 `07-55-41-457Z` 已有样本——若选此项，须在 `docs/113` 写明样本来源不一致。
   - **(b) 评测工作区**：默认**保留** `~/Desktop/study/ai-se-eval/{S1,S3,L1}`（阶段 B 出口复测可能复用 L1；目录本身不在开发库内、不污染项目数据）。选择清理须在 `docs/113` 记录。
   - **(c) `docs/110` 更新粒度**：默认**只补写实测事实**（状态、ID、清理实况），保留原有结论与「部分完成」措辞，不改写历史判断。
5. **证据锚点**：每个动作留「命令 + 退出码/HTTP 状态 + 关键 ID（projectId / requirementId / workflowId）+ 结果文件路径」，写入 `docs/113`。
