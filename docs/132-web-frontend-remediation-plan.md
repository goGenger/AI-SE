### W2 · 拆除双样式体系（P2）——**根因，先做这个**

**目标**：全站只剩一套样式来源，彻底消灭优先级冲突。

**为什么必须排在视觉之前**：只要 `styles.css` 还在，`styles/app.css` 的令牌就继续被覆盖。不拆它，W3 之后所有视觉调整都会"改了不生效"，白做一轮。

**工作项**

1. 清点 `styles.css`（约 960 行）每一条规则，分三类：
   - (a) 仍被使用 → 迁到对应 Vue 组件的 scoped style，或改写为 Tailwind 工具类
   - (b) 零引用死类 → 删除（**自己 grep 精确确认，不采信审评清单**）
   - (c) 真正的全局基础（盒模型 / `body` / 字体 / 滚动条 / `focus-visible`）→ 迁进 `app.css` 的 `@layer base`
2. 重点处理全局 `a` 规则：**不要**把「链接一律青绿 + hover 下划线」带进新体系。改为链接默认继承颜色，只在确为正文链接处显式声明。
3. 删除 `styles.css` 本体与 `main.ts:6` 的引入。
4. 删掉 11 处对抗补丁（`AppSidebar` + 10 个 view；`RequirementsView` 本就没有），另加 `Table.vue` 里对抗 `font: inherit` 与 legacy 单元格排版的补丁。**补丁存在的唯一理由是 `styles.css`，它删了补丁必须一起删。**
5. 建立层级顺序：`@layer base` → `components` → `utilities`，工具类必须能覆盖组件层。
6. **同步更新 `__tests__/` 的 class 断言**（约 10 个文件受影响，其中 `uiComponents.test.ts` 61 处、`commonComponents.test.ts` 13 处），报告里逐条列出改了什么、为什么。

**验收（自行执行并贴出结果）**

- `grep -rn "styles.css" apps/web/src` → 0
- `grep -rn "!important" apps/web/src --include=*.vue --include=*.css` → 0
- 逐页确认颜色只来自令牌，无硬编码 hex（仅令牌定义文件允许出现 hex）
- §0 四条命令全绿

**交付**：`docs/134-phase-w2-single-stylesheet.md`

**风险**：这是本次改造中 DOM/class 破坏面最大的一步。23 个测试文件里含结构断言的会集中变红——这是**预期内**的，不是回归，必须在同一提交内更新完再跑。

### W3 · 重建设计令牌与排版（P3）

**目标**：一套「专业克制」的令牌体系，全站视觉语言唯一且可推导。

**工作项**

1. **字体先裁决**。当前 Jost 两个问题：几何展示字体在 12–14px 密集界面可读性差；从 `fonts.googleapis.com` 加载，在 Asia/Shanghai 环境经常不可达 → 回退到系统字体、字形字宽变化、布局抖动（**等于这个字体很可能在本机根本没生效**）。二选一：
   - (a) 系统性系统字体栈（中文 PingFang SC / Microsoft YaHei，西文 Inter 或系统 UI）
   - (b) 自托管到 `apps/web/public/fonts/`，不依赖外部 CDN
   - 无论哪条，**数字必须真等宽（tnum）**。当前表格用了 `tabular-nums`，但 Jost 不保证提供——需实测，没生效就换字体。
2. 重写 `styles/app.css` 令牌，形成完整刻度：
   - 间距：4px 基准单一刻度，禁止 17/19/23px 这类值
   - 字号：只留 6–7 档，每档明确 字号/行高/字重 三元组，并规定「什么场景用哪档」
   - 圆角 3–4 档；边框 default/strong 两档并规定用法
   - 阴影极轻，且写明「普通卡片优先用边框而非阴影」（`00-design-system.md` §7）
   - 焦点环统一一档，必须清晰可见
3. 语义色 success/warning/danger/info/neutral，每色给 bg/border/foreground 三档；**所有前景背景对比度实测**（正文 4.5:1、大字与图形 3:1），把实测值写进报告。
4. 定义亮色 + 暗色两套，并在 `:root` 声明 `color-scheme`。
5. 统一断点：当前混用 `min-[900px]`/`min-[800px]`/`min-[540px]`/1180px 等，收敛到 Tailwind 具名断点（sm 640 / md 768 / lg 1024 / xl 1280）。
6. 清剿任意值：`text-[72px]`、`min-[900px]`、`w-[240px]`、`w-[200px]`、`min-w-[1100px]` 等（实测命中见 §1），改完后 grep 确认 `src/views/` 与 `src/components/` 内不再有 `[]` 形式的一次性尺寸。

**交付**

- `apps/web/src/styles/README.md`：每档用途 + 「新页面应该怎么选」（用户将以此检查后续改动是否守规矩）
- 更新 `docs/design/00-design-system.md`：§3 颜色表、§4 字体表述改到与实现一致；废弃部分明确标注「已废弃」（依赖 §2 冲突 1 的裁决）
- `docs/135-phase-w3-tokens-and-typography.md`

**停止点**：令牌定稿后停下来看效果再往下走——这一步决定全站视觉语言。

## 4. 依赖顺序与检查点

```
W1 诊断/基线归零
 └─ W2 拆双样式体系 ◄── 根因，必须最先做
     └─ W3 令牌与排版 ◄── 决定全站视觉语言
         └─ W4 AppShell 与信息架构（PageContainer 在此诞生）
             └─ W5 页面骨架统一（依赖 PageContainer）
                 ├─ W6 仪表盘
                 ├─ W7 表格
                 ├─ W8 交互容器
                 └─ W9 可访问性与韧性
                     └─ W10 终验
```

**为什么不能跳步**（摘自审评，机械依赖而非偏好）：

- 先拆双样式（W2）再动视觉。否则改的 token 依然被覆盖，等于白干一轮。
- 先建令牌与排版（W3）再改页面。否则 11 个页面会各自长出自己的视觉语言——这正是问题 2 的成因。
- 先统一骨架（W5，依赖 W4 的 `PageContainer`）再逐页改造。否则同样的活要干 11 遍。

**审评建议的推进节奏**（本计划采纳）：W1 单独一轮 → W2 单独一轮（做完先感受"原来改样式真的会生效"）→ W3 单独一轮（值得反复看效果）→ W4–W9 按模块推进，每模块跑测试 + 看截图 → W10 收口。

**中间纠偏**：某一轮方向不对就直接回滚重来，比在错的基础上打补丁便宜。本仓库无 git，**回滚依赖阶段前的文件清单快照**——因此每个阶段开工前先记录将改动的文件清单。
