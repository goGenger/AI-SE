## 0. 为什么现在做这一批

1. **它废掉了唯一的花费控制。** 批次脚本的止损线是「周配额代理值 ≥ 200M 就停」，而代理值的唯一来源是 `agent_runs.token_usage`。**一条坏值（2.6×10¹⁷）就足以让守卫在下一次 run 前无条件掐断**——L1-M4f 已经实际发生过一次（run 2 因此差点跑不起来，靠用户裁定「抬守卫」才继续）。
2. **它是确定性缺陷，不是随机故障**（§2.3 的 4/4 相关）。**确定性意味着它会重复发生**：下一次跑到守卫的批次会再次产生坏值、再次废掉守卫。
3. **它是被 N-7 遮住才第一次露头的**（§2.4）。PL-M14 之前框架的 25 超步先掐断，平台守卫**根本够不到**，这条路径从未执行过。**N-7 修好之后，N-8 必然暴露**——这不是巧合，是因果。
4. **它同时污染记账**。`docs/146` §5 的批次成本、`docs/127` §6 的配额快照都从这张表读数；坏值不清理，所有后续的成本口径都不可信。

### 2.4 为什么今天才出现：**N-7 遮住了 N-8**

`AgentGraph.ts:229-238` 的平台守卫要求 `state.iteration >= options.maxIterations`（生产路径 50）。**PL-M14 之前，外层图在 LangGraph 默认的 25 超步（约 13 轮）就被框架掐断，`state.iteration` 从未达到 50**——守卫分支从未执行。**PL-M14 让守卫可达，N-8 随即出现**：4 条坏值全部在 PL-M14 之后（10-17 09:08 起）。

> **〔勘误 2026-10-17，见 §9〕** 本节把「跑到守卫」理解为**迭代数累积到 50**，**这个框架是错的**。实测（`docs/177` §2 更正 1）：`DeepAgentLLMProvider.invoke` 交回 `agentIterations = ToolRuntimeBackend.iterations`（**内层** deep agent 的工具执行计数），而 `responseIteration` 取 `Math.max(state.iteration + 1, agentIterations)`——**`state.iteration` 一步可以跳很多格**。探针里 S1 的工具调用轮号是 `1,2,…,8,**50**`：前 8 轮每轮一次，**第 9 轮一步跳到 50**，下一轮命中守卫。
>
> **⇒ 「50」是内层工具执行计数，不是外层循环次数。** 外层只跑了约 9 轮。
>
> **一处未解决的张力（登记为开放项）**：本节的第二条子断言——「PL-M14 之前框架先掐断，守卫够不到」——与 10-15 的 E1 实测**存在张力**：那天 96 个 run 的 `current_iteration` 超过 12、最高 88，却**零递归上限错误**（`docs/177` 未解决该张力，因外层轮数不可测，见其 §2 补充 4）。**本节结论方向未变（N-8 只在守卫路径上出现，11/11），但「为什么 PL-M14 之前够不到」的机制描述不足以采信。**

### 2.5 机制：**累加器已被排除，未排除的是「喂进去的值」**

**本任务书起草时的探针实测**（`scripts/probe-usage-accounting.ts`）：用一个**每次调用都返回同一份用量**（`input=1000, output=200`）的脚本化 provider，在 `maxIterations = 2 / 4 / 8 / 16 / 50` 下各跑一次，读 `result.tokenUsage`：

```
maxIter   calls  input_tokens   expected   ratio
      2       2          2000       2000   1.000e+0
      4       4          4000       4000   1.000e+0
      8       8          8000       8000   1.000e+0
     16      16         16000      16000   1.000e+0
     50      50         50000      50000   1.000e+0
N8-LINEAR
```

**⇒ 平台的累加口径（`packages/agent-core/src/llm/usage.ts` 的 `sumTokenUsage`，纯递归求和、无乘法）是正确的，`agentNode` 的逐轮累加也是正确的。** 膨胀**不在累加这一环**。

**⇒ 剩下的唯一未排除环节是「provider 交回的 `usage_metadata` 本身」**——即 `DeepAgentLLMProvider.invoke` 返回的那个值（来自内层 deep agent）。**这是本批要查的那一环。**

**一处已实查但不足以定论的事实**：`AgentGraph.ts:139-144` 的 `usageMetadata(response)` 返回的是 `response.usage_metadata` **引用本身**（不做拷贝）；`metadata` 通道的 reducer 是浅合并 `(left, right) => ({ ...left, ...right })`。这两处**都不能解释 10¹⁷ 量级**——探针已用固定值证明累加不会放大。

> **〔追加 2026-10-17，见 §9〕** 本节结论（**累加环已排除、剩下的唯一未排除环节是 `DeepAgentLLMProvider.invoke` 交回的 `usage_metadata`**）**不变且被便宜档探针独立复现**（7/7 都在守卫路径上）。§9 另记一条**明确标注为假设、未经验证**的候选机制，供 §5 第 1 层探针去证实或证伪——**不得当作结论使用**。

### 2.6 与 N-8 无关但同批暴露的观察（**不在本批范围**）

L1-M4f run 2 的 `T-01` **成功产出了合格的结构化提交**（`outcomeMode: "tool"`，26 条判据、六组 `EC-SCR` / `EC-ENV` / `EC-TC` / `EC-LINT` / `EC-TST` / `EC-IGN`），**但任务仍判 FAILED**——因为 agent run 以 `TOOL_ERROR` 结束。⇒ **真问题不是「没提交」，是「提交得太晚，把 50 轮预算烧光了」**。这是**计划/任务粒度或提示词**层面的问题，**与本批的记账缺陷无关**，**不在范围内**。

### 2.7 影响面

- **任何按用量计价 / 限额的下游**（`estimated_cost` 虽因未配置价目而为 `NULL`，一旦配置即受影响）。

## 4. 设计裁定（本任务书的推荐值）

| # | 事项 | 推荐值 | 理由 |
| --- | --- | --- | --- |
| 1 | 修法形态 | **先探针定位（15b），再定点修**；不预设改动面 | §2.5 只排除了一环（累加），另一环（provider 交回的值）**完全未测**。先改后验会把「碰巧好了」当成「修好了」——N-6 / N-7 两次都证明了这一点 |
| 2 | 探针手段 | **复用 N-6 的手法**：真实 `DeepAgentLLMProvider` + **录制型假网关**（离线、可复现、零配额），把**每轮 provider 交回的 `usage_metadata`** 落盘 | 这是唯一能同时满足「真实内层 agent」与「不花配额」的手段；N-6 已验证该手法可用（`scripts/probe-gateway-message-shape.ts`） |
| 3 | 守卫健壮化与根因修复的关系 | **两件事分开裁定、同一批做** | 根因修复（15c）可能**不可得**（若坏值来自第三方库或网关，平台侧只能防）。而守卫**必须**不再被单条值废掉——它是唯一的花费控制。**分开裁定**是为了让「根因没修好」不阻塞「守卫已健壮」 |
| 4 | 守卫健壮化的形态 | **优先「合理性上界」而非「统计离群」**：单个 agent run 的 `input_tokens` 不可能超过某个可论证的上界（例如 `maxIterations × 单轮上下文上界`），超出即视为异常值并**在守卫侧忽略**（不写库、不改历史行） | 简单、可解释、无需调参；统计离群法需要历史分布且会随平台演进而失效 |
| 5 | 是否改 `packages/eval` 的守卫逻辑 | **改**，但**只改守卫的读取口径**，不动 `EvalPolicy` / 夹具 / oracle / L1-8 判据 | 守卫在 `packages/eval/scripts/*.sh` 里，属评估工具链；红线是 `EvalPolicy` 与夹具，不是批次脚本 |
| 6 | 是否顺带修 `T-01` 烧满 50 轮 | **不做** | §1 第 6 项：不同源，混批会让归因变糊 |
| 7 | 探针是否入库 | **是**，落 `packages/agent-core/scripts/` | N-6 / N-7 的先例；`packages/eval` 不依赖 `@ai-se/agent-core` / `@langchain/*`，裸导入解析不到 |

**被否掉的方案（记录，避免重复推演）**：

| 方案 | 否决理由 |
| --- | --- |
| **A｜直接删掉/清零那 4 条坏值** | `AGENTS.md` §6 红线：不修改历史 `agent_runs` 行。且**治标不治本**——下一次跑到守卫会再产生一条 |

## 9. 追加块（2026-10-17）：便宜档探针的实测补充

### 9.1 实测：N-8 在便宜档上复现 **7/7**

夹具 **S1** 与 **M1** 各跑 1 轮（`--autonomy-l1 --replan`，与 l1-m4f 同策略）：

| M1 | `986ae8a6` | 4 | **50 / 50 / 50 / 50** | 全部 `TOOL_ERROR` | 4.7×10¹⁴ / 3.8×10¹⁶ / 1.6×10¹⁶ / 2.5×10¹⁶ |

**7 个 agent run 全部撞到守卫、全部产出坏值**；消息一律 `Agent reached max iterations`。**两个夹具都死在第一个切片**（S1 的任务是「实现 `slugify` 函数」，M1 是「补齐 todo 服务的 PATCH / DELETE / 过滤」）。

### 9.2 更正：**本任务书起草时的离线判断是错的**

起草时据 2026-10-07 的 S/M/L 数据（`current_iteration` 最高 38、`≥50` 为 **0/222**）判断「便宜档到不了守卫，不会复现 N-8」。**实测推翻**：当前 agent 上，两个便宜夹具的**每一个** agent run 都撞到守卫。**该判断不再出现在本任务书的任何依据里。**

### 9.3 更正：守卫的触发机制（**并入 §2.4 的勘误**）

「50」是**内层**工具执行计数（`ToolRuntimeBackend.iterations`，经 `agentIterations` 交回、被 `responseIteration` 取 `max`），**不是外层循环次数**。S1 的工具调用轮号 `1..8, 50` 是直接证据：外层只跑约 9 轮。**完整链路见 `docs/177` §2 更正 1。**

### 9.4 新事实：**外层轮数从库里测不出来**

`tool_calls.iteration` 有两个写入方（外层 toolsNode 写 `state.iteration`，内层 backend 写自己的计数器），`onIteration` 只更新 `current_iteration` 不写事件。**⇒ 库里没有任何字段等于外层超步数。** 详见 `docs/177` §2 补充 4。**这条对本任务书的直接影响**：§2.4 那条「PL-M14 之前框架先掐断」的子断言**无法用库数据校验**，已在 §2.4 登记为开放项。

### 9.5 一条**未验证的假设**（供 §5 第 1 层探针处置，**不得当结论**）

`DeepAgentLLMProvider.ts:87` 的 `totalTokenUsage(agentUsages(result))` 遍历内层 deep agent 的**整份 message 列表**，而那份列表包含外层回灌进来的历次 `AIMessage`——每条都携带**上一轮已累加过**的 `usage_metadata`，于是跨轮**复合**而非相加。**该假设未经任何测量验证。** §5 第 1 层（真实 `DeepAgentLLMProvider` + 录制型假网关，逐轮落盘）应当先证实或证伪它，再决定改动面——**§4 裁定 1「先探针定位，再定点修」不变**。

### 9.6 对 §7 待裁定项的影响

**七项推荐值一条不改、一条不撤。** 但第 3 项（守卫健壮化形态＝**合理性上界法**）本轮多了一条实测支撑：**探针两次亲历守卫被单条坏值废掉**——第一次是抬阈值才能启动，第二次是 S1 自己产出的 3 条坏值把冻结的止损线顶穿、批次被掐断（`docs/177` Implementation 偏离 1/2）。**且这是唯一的花费控制。**
