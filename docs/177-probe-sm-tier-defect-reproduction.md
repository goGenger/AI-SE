## §2 对 `docs/176` 的补充与更正

### 更正 1：守卫的触发机制不是「agent 循环 50 次」

`docs/176` §2.4 的框架把「跑到守卫」理解为**迭代数累积到 50**。实测不是这样。

链路（逐处代码实查）：

1. `DeepAgentLLMProvider.invoke` 交回 `agentIterations: this.backend.iterations`（`DeepAgentLLMProvider.ts:99`）。
2. `ToolRuntimeBackend.iterations` 的取值是 `Math.max(1, this.iteration + 1)`（`ToolRuntimeBackend.ts:159-160`），而 `this.iteration` 是**内层** deep agent 的**工具执行计数**——`executeTool`（`:414`）与 `recordDeniedCall`（`:338`）各 `+= 1`。
3. `AgentGraph` 的 `responseIteration` 取 **`Math.max(state.iteration + 1, agentIterations)`**（`AgentGraph.ts:155-160`）。
4. `agentNode` 顶部判 `state.iteration >= options.maxIterations`（`AgentGraph.ts:229`）。

**⇒ `state.iteration` 一步可以跳很多格。** S1 的实测形状把这一点摆得很直白：

```
tool_calls.iteration : 1, 2, 3, 4, 5, 6, 7, 8, 50
                        ^^^^^^^^^^^^^^^^^^^^^  ^^
                        前 8 轮每轮一次调用      第 9 轮直接跳到 50
```

前 8 轮是 `git_status / list_directory / read_file×3 / search_code×2 / submit_result`，**第 9 轮一步跳到 50**，下一轮 `agentNode` 顶部命中守卫 → `TOOL_ERROR`。

**⇒ 「50」是内层工具执行计数，不是外层循环次数。** 这同时解释了 N-7 为何在这些 run 上不出现：**外层只跑了约 9 轮**，远不到 25 超步。

### 更正 2：便宜档**会**复现 N-8（推翻了 §0 的离线判断）

两个便宜夹具的**每一个** agent run 都撞到守卫并产出坏值。详见 §3 测量结果。

### 补充 3：相关性由 4/4 收紧到 **11/11**

全历史 `input_tokens > 10,000,000` 的行现为 **11 条**，**全部** `current_iteration = 50` **且** `error->>'message' = 'Agent reached max iterations'`，**零例外**；反向：`11/11` 全部带坏值。其中 4 条来自 L1-M4f（09:08–09:22）、3 条来自本轮 S1（09:55–09:57）、4 条来自本轮 M1（10:29–10:31）。

**「迭代数多」依旧被排除**（`docs/176` §2.3）：81 轮 / 404,844、61 轮 / 347,699 等全部正常。

### 补充 4：外层轮数**从库里测不出来**（`docs/176` 未涉及）

`tool_calls.iteration` 有**两个写入方**：

- `AgentGraph` 的 toolsNode 写 `state.iteration`（`AgentGraph.ts:328` / `:336` / `:351`）；
- `ToolRuntimeBackend` 写它自己的计数器（`:341` / `:365` / `:375` / `:439` / `:443` / `:451`）。

而生命周期回调 `onIteration` **只更新 `current_iteration`、不写事件**（`agentRunService.ts:480-485`）。

**⇒ 库里没有任何字段等于外层超步数。** 因此**任何**「便宜档到不了 N-7 那个深度」的历史论证都不成立——包括我在本轮之前用 `tool_calls.iteration` 去重数做的那个（**该代理无效，已撤回**）。

### 补充 5：坏值机制仍未定，但候选环收窄到一处

`docs/176` §2.5 用探针排除了**累加环**（`sumTokenUsage` 线性）。本轮实测给出的新线索是：坏值**只在守卫路径上出现**（11/11），而守卫路径的特征是「内层计数被抄进 `state.iteration`」。

**唯一未被排除的环仍是 `DeepAgentLLMProvider.invoke` 交回的 `usage_metadata`**（`DeepAgentLLMProvider.ts:87` 的 `totalTokenUsage(agentUsages(result))`）。

**一条未验证的假设（明确标注为假设，不作为结论）**：`agentUsages(result)` 遍历内层 deep agent 的**整份 message 列表**，而那份列表包含外层回灌进来的历次 `AIMessage`——每条都携带**上一轮已累加过**的 `usage_metadata`，于是跨轮**复合**而非相加。**该假设未经任何测量验证**，PL-M15 若要采用，必须先按任务书 §5 第 1 层（真实 `DeepAgentLLMProvider` + 录制型假网关）实测。

## Known Issues

1. **本轮探测自身的成本读不出来**（§3.4）。任何跑到守卫的批次都有这个问题，直到 N-8 修好。
2. **外层轮数从库里测不出来**（§2 补充 4）。这直接导致「N-7 能不能被便宜档复现」**本轮没有答案**——观测上 N-7 是 0 次，但**无法证明**那是因为轮数没到。**登记为观察项**。
3. **守卫口径在探测脚本里与平台不一致**（有界求和），**这是有意的**：平台的守卫在被污染时无法读数。探测脚本的口径**不构成平台侧改动的依据**——`docs/176` §7 第 3 项仍是待裁定。
4. **服务端复用是静默的**（`docs/169` KI 8）。本轮靠**手工核实实例启动时刻 vs `dist` 构建时刻**才确认复用正确。该 KI 维持登记。
5. **便宜档不是 E1 的完整替代**：本轮复现了 N-8，但 N-6 与 N-7 都是 0 次（N-7 且无法判定）。它覆盖的是「**烧穿预算 / 守卫**」这一类，不是全部。
6. **`--replan` 在两个夹具上都带**——与 e2b 的惯例一致（每个夹具的 run 1 都带），但这**不是** l1-m4f 合同里「只有 run 1 带」的字面形状。记在这里以免将来被读成偏离。
7. 前几批的未修项全部维持登记（读侧放行 / 根级源码文件 / `scripts/` / `test/` / `canonicalAcKey` 副本 / N-1b / N-1c / N-3 / 7b / `CHECK_CANDIDATES` / 启动器陈旧实例 / 库内孤儿行 / `T-01` 烧满 50 轮）。
