### 2.3 平台侧没有 thinking 开关（实查）

`createOpenAIChatModel`（`LangChainLLMProvider.ts:143-157`）只传 `model` / `apiKey` / `temperature` / `configuration`（`baseURL` + 合规头 + UA 改写）。**平台没有任何开关控制网关是否进入 thinking 模式**——这一点与 `docs/173` KI 6「网关何时要求回传仍不可控」一致。

### 2.5 首选假设（**假设，不是结论**）

> **H-A**：400 的产生条件是「**出站请求里存在一条带 `tool_calls` 但没有 `reasoning_content` 的 assistant 消息，且网关处于 thinking 模式**」。

**支持它的三条实查事实**：

1. 补丁的回传条件是「**消息自身**携带**非空** `additional_kwargs.reasoning_content`」（`completions.js:588` 的三重条件）。
2. 响应侧存入的条件是 `providerReasoningContent !== void 0`（`:175`）——**网关没给，平台就永远没有**，且平台**无法凭空造出**它。
3. 网关**间歇性**进入 thinking 模式（`docs/129` / `docs/173` KI 6）。若同一会话里早先的轮次网关没给 reasoning，那些轮次产出的、**带 `tool_calls` 的** assistant 消息在网关切到 thinking 之后就会缺字段。

**H-A 成立时的可修点分析（供 §7 裁定，不作为结论）**：平台无法伪造 `reasoning_content`，所以平台侧能做的只有**改变那条消息在后续请求里的形状**，或**对 400 做一次降级重试**。两者都是**语义改动**，必须先由探针证明 H-A 成立才谈。

**被否的备选假设**：

| 假设 | 否证 |

| **H-B**：PL-M16 剔除 `tool_calls` 导致网关认为「这条 assistant 消息本该带 reasoning 却没带」 | 与 H-A 的差别在于「谁剔的」。**未否证，但优先级低**：run 1 同构建零条；且五个失败 run 都死在内层（外层那条消息根本没机会被送出） |
