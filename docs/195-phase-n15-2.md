# 195 · N-15′：DEBUG 任务没有类型级检查（一个会写生产代码的任务类型没有验证门）

> 立项：2026-10-20。缺陷登记于 `docs/146` §3（L1-M4l 暴露）与 `docs/188` §Known Issue 7′。
> 基线：`docs/194`（N-20，`errorTypes` 双粒度相加）。
> 状态：**已修复**。包内门禁全绿；**未在真实批次验证**。

## 1. 缺陷与根因（file:line）

**现象**：DEBUG 任务**恒不可验证**。库内 38 条带验证记录的 DEBUG 任务里 **33 条** verdict 为
`unavailable`，原因串**逐字**为 `no available checks for task type DEBUG`；另 5 条 `failed`
**全部来自防篡改**（`protected test files modified`），**没有一条来自检查**。

**而 DEBUG 是会写生产代码的**，三条代码事实叠起来：

| # | 事实 | 位置 |
| --- | --- | --- |
| 1 | DEBUG **在 `DEV_TASK_TYPES` 里** ⇒ 平台**已经**把它当写代码的任务对待（执行前做受保护测试文件快照、执行后做写范围审计） | `taskVerifierRules.ts:46`、`verifyingTaskExecutor.ts:40` |
| 2 | DEBUG 任务**不派给「DEBUG agent」**——`task.type` 被换成 `input.targetTaskType` 再派发 | `AgentRegistry.ts:318-319` |
| 3 | 于是 `DEBUG→DATABASE` 跑的是 **database agent**，会改 `src/schema.js` / `src/migrations.js`（`T3-DEBUG-1-DEBUG-2` 实测） | `docs/188` §Known Issue 7′ |

**唯独检查面漏了**：`CHECK_CANDIDATES`（`taskVerifierRules.ts:49-54`）只有
`BACKEND` / `FRONTEND` / `TEST` / `BUILD`，`DATABASE` 另走迁移分支（`:82-99`）——
**没有 DEBUG 项** ⇒ `candidates = []` ⇒ 计划恒为空 ⇒ 走 `taskVerifier.ts` 的
`plan.plans.length === 0` 分支 ⇒ `verdict = "unavailable"`。
而 `verifyingTaskExecutor.ts:77` 只覆盖 `verdict === "failed"` ⇒ **任务照判 SUCCESS**。

> **⇒ 一个会写生产代码的任务类型没有验证门。**

---

## 2. 修法：DEBUG 按其 `input.targetTaskType` 取检查

**判据：DEBUG 任务的检查类型 = 它的目标类型。** 理由全部指到既有代码，不引入新语义：

1. **与派发侧同构**：`AgentRegistry.ts:318-319` 已经用目标类型决定**谁来做**；用同一个类型决定
   **怎么验**，是同一件事的另一面。做的是 database agent 的活，就该受 database 的检查。
2. **与计划侧同源**：目标类型的判定用 `@ai-se/shared` 的 **`isUsableTargetTaskType`**
   （`packages/shared/src/index.ts:500`）——`WorkflowEngine.debugTargetType`（`:63-74`）与
   `AgentRegistry.debugTarget`（`:263-266`）用的就是它。**不另立第三张表**：
   「重复定义必然漂移」是本仓库已登记的缺陷成因类型（`docs/160`，PL-M10 / PL-M12 同因）。
3. **目标缺失/不可用时回落 `DEBUG`** ⇒ 计划仍为空 ⇒ 与今天**逐字一致**（`unavailable`）。
   **只会变好，不会把原本能判定的任务变成不可判定。**
4. **目标可用但该类型本身没有候选检查**（`DEPLOY` / `REVIEW` / `DESIGN` / `ANALYSIS`）⇒
   仍是空计划 ⇒ 仍是 `unavailable`。**路由不等于造门。**

**红/绿灯语义仍按任务自身类型判定**（`taskVerifierRules.ts` 里 `candidate === "test" && taskType === "TEST"`）：
红灯表达的是「这个任务负责**写**测试」，属于任务**自身**的类型。`DEBUG→TEST` 的任务是去**修**测试，
要求测试先红是错的。同理，PL-M9 9c 的 TEST fail-closed（`taskVerifier.ts:564`）也**故意**仍按
`task.type === "TEST"` 判定——「红灯检查是它存在的全部理由」只对 TEST 任务成立。

**库内分布支持这个设计**（全库 54 个 DEBUG 任务）：

| `input.targetTaskType` | 个数 | 修后是否可判定 |
| --- | --- | --- |
| `BACKEND` | 46 | ✅ 有候选检查（`build` + `test`） |
| `DATABASE` | 5 | ✅ 有候选检查（`migrate-up` / `migrate-down`，成对声明才算可用） |
| `BUILD` | 2 | ✅ 有候选检查（`build`） |
| 缺失 | 1 | ❌ 回落 `DEBUG` ⇒ 与今天一致 |

**⇒ 53 / 54 会路由到有候选检查的类型。**

**修后在真实工作区里检查是「可用」的**（不是空跑）：L1-M4m run 3 收尾态的真实 E1 工作区
（`~/Desktop/study/ai-se-eval/E1/run-1`）的 `package.json` 声明了
`build` = `node infrastructure/selfcheck.mjs build`、`test` = `node --test`
⇒ `DEBUG→BACKEND` 会真的跑起这两条检查。

## 4. Implementation

```ts
// taskVerifierRules.ts（新增）
export function effectiveCheckType(taskType: TaskType, targetTaskType: unknown): TaskType {
  if (taskType !== "DEBUG") return taskType;
  return isUsableTargetTaskType(targetTaskType) ? targetTaskType : taskType;
}

// resolveVerificationChecks：第三参缺省 = taskType（既有调用方零改动）
export function resolveVerificationChecks(
  taskType: TaskType,
  scripts: Record<string, unknown>,
  checkType: TaskType = taskType
): VerificationCheckResolution {
  if (checkType === "DATABASE") { … }
  const candidates = CHECK_CANDIDATES[checkType] ?? [];
  …
  expectation: candidate === "test" && taskType === "TEST" ? "fail" : "pass"   // ← 仍是 taskType
}

// taskVerifier.ts（唯一的调用点）
const plan = resolveVerificationChecks(
  task.type,
  facts.scripts,
  effectiveCheckType(task.type, task.input.targetTaskType)
);
```

**改动量**：1 个新函数 + 1 个可选形参 + 1 处调用点。**没有新增表、没有新增谓词、没有改判定分支。**

## 7. Tests

`corepack pnpm --filter @ai-se/server test` → **50 files / 318 tests 全通过**（改动前 306，**+12**）。

**纯规则层（`taskVerifierRules.test.ts`，8 例）**：
- 非 DEBUG 任务不受 `targetTaskType` 影响（恒等于自身类型）。
- DEBUG 取可用目标；**运行期专属**类型（`DEBUG` / `MONITOR` / `INCIDENT`）与非法值回落 `DEBUG`。
- **目标可用但该类型没有候选检查**（`DEPLOY` / `REVIEW` / `DESIGN` / `ANALYSIS`）⇒ 空计划
  ——**路由不等于造门**。
- DEBUG 走目标类型的检查计划（`BACKEND` → `build`+`test`；`DATABASE` → 迁移对）。
- 目标类型的 script 缺失时**证据面缺口可见**（`missing` 非空，PL-M9 9a 语义保留）。
- 目标缺失时回落 `DEBUG`：计划与 `missing` 均为空（**与修前逐字一致**）。
- **红灯仍按任务自身类型判定**：`TEST` → `expectation: "fail"`；`DEBUG→TEST` → `"pass"`。
- 第三参缺省等于 `taskType`（既有调用方一字不改）。

## 11. Known Issues

1. **未在真实批次验证。** 本项只做到「包内门禁全绿 + 库内分布普查 + 真实工作区脚本可用性核对」，
   **下一次 E1×3 批次的 `run-*.json` 与 `tasks.output.verification` 才能确认**。按纪律，
   **不判「已关闭」**。
2. **本项会让此前「不可判定」的 DEBUG 任务变成可判定，因此可能让批次数字变差——这是门在起作用，
   不是变坏。** 修前 DEBUG 任务的 verdict 恒为 `unavailable`、任务照判 SUCCESS（等于免检）；
   修后它会真的跑 `build` / `test`，跑不过就 FAILED，进而走重试 / replan。
   **预期净效果**：把「DEBUG 任务改坏了工作区」从**晚**（staging VERIFY）提前到**早**（任务级检查），
   并把它**归因到具体任务**。**这一条是推理，不是实测**——下一批的 `stagingSegment` 才能验证
   「它没有把本来能过的批次拖坏」。
3. **`verificationUnavailableByType.DEBUG` 会从非零掉到接近 0。** 这是本修复的**目的**，
   不是指标变坏；但**跨批次的该字段不可直接比较**（修前/修后口径不同）。同理
   `verificationUnavailable` 总数会下降。
4. **`no available checks for task type ${task.type}` 这条 reason 串在路由后会略失准**：
   `DEBUG→BACKEND` 且工作区缺 `build`/`test` 时，串仍说「no available checks for task type DEBUG」，
   而真相是「有候选检查但工作区缺 script」。**证据面并未丢**——`missingChecks` 字段照实记
   （PL-M9 9a 的机制，`taskVerifier.ts:575-584`）。**这是既有措辞的既有精度问题（PL-M9 9a 已用
   `missingChecks` 补偿），本次不改**，以免动一条被 `docs/188` §Known Issue 9 逐字引用的串。
5. **`DEBUG→TEST` 的不可裁决情形不 fail-closed。** 9c 只对 `task.type === "TEST"` 生效；
   `DEBUG→TEST` 且工作区缺 `test` script 时按 `unavailable` + `missingChecks` 记账。
   **这是有意的**（见 §2），但**库内 0 例**，故**未经真实数据检验**。
6. **`DEPLOY` 等「可用但无候选检查」的目标不会因此获得门。** 若日后发现 DEBUG 任务真的落在
   `DEPLOY` 上做交付工作，须另立一项（`CHECK_CANDIDATES` 目前没有交付链类型的检查，
   交付走 `collectStagingSegment` 的 staging 段判据）。
7. **历史任务记录不回填。** 修前落盘的 33 条 `unavailable` 是当时的观测记录，
   按 `docs/146` §6 规则 7 冻结，勘误只以追加块登记（本文件即该追加块）。
