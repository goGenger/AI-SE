## 2. 普查

### 2.1 机制：三档优先级，三档里有两档从未被用过

`resolveTaskTimeoutMs`（`apps/server/src/services/workflowTaskExecutor.ts:76-85`）：

```
task.input.execution.timeoutMs  >  taskTimeoutByType[task.type]  >  taskTimeoutMs  >  120_000
```

| 档 | 来源 | 全库实况 |
| --- | --- | --- |
| 任务级 `execution.timeoutMs` | 计划/人工写入 | **只有 1 个任务设过**（`SELECT count(*) FROM tasks WHERE input->'execution'->>'timeoutMs' IS NOT NULL` = 1） |
| 类型级 `TASK_TIMEOUT_MS_BY_TYPE` | `config.ts:57` | **从未配置**（`.env` 无此键） |
| 全局 `TASK_TIMEOUT_MS` | `config.ts:52` | **600s（本次改动前）**，`.env` 未覆盖 ⇒ 所有任务类型一律 600s |

⇒ **平台有两个更细的旋钮，一个都没拧过**；全部 3742 次 run 走的是同一个全局值。
`maxIterations` 则**硬编码**在 `workflowTaskExecutor.ts:302`（`50`），不可配置。

### 2.2 全库读数：87 / 3742（2.3%），横跨全程，**不是回归**

```sql
SELECT count(*) FILTER (WHERE error->>'code'='TIMEOUT_ERROR') AS timed_out,
       count(*) FILTER (WHERE status='timed_out') AS status_timed_out
FROM agent_runs;   -- 87 / 85（总 3742）
```

最早 `09-28 09:01`、最晚 `10-19 15:35`——**从脚手架期到现在一直存在**，不是某次改动引入的回归。

**分母要说清**：87 条里有 **9 条没有对应的 `tasks` 行**（`agent_runs.task_id` 无外键，任务行可被删而 run 留存），
且**全部落在 `09-29` / `09-30`**，时长是 180 / 973 / 1411 / 212 / 180 / 1016 / 840 / 180 / 1013 秒——
**不是 600s 档**，属**均匀 600s 生效之前**的遗留行。⇒ **本文的形状普查（§2.4）一律以「有任务行的 78 条」为基数**，
不用 87。

### 2.3 时间花在哪：**模型回合，不是工具**

对最近 7 个实例（`I1` / `I3-REPLAN-1` / `T-02` / `T-02-DEBUG-1` / `TASK-010` / `T-007` / `T-008`）逐 run 汇总
`tool_calls.duration`：

| 任务 | 工具调用次数 | 工具执行合计 | 单次最长 | 600s 里工具占 |
| --- | --- | --- | --- | --- |
| `I1` | 24 | **5,123 ms** | 363 ms | 0.9% |
| `I3-REPLAN-1` | 50 | 18,623 ms | 3,621 ms | 3.1% |
| `T-02` | 65 | 18,946 ms | 1,114 ms | 3.2% |
| `T-02-DEBUG-1` | 65 | 17,232 ms | 1,134 ms | 2.9% |
| `TASK-010` | 48 | 17,793 ms | 7,293 ms | 3.0% |
| `T-007` | 62 | 55,411 ms | 41,025 ms | 9.2% |
| `T-008` | 72 | **141,782 ms** | 42,644 ms | 23.6% |

⇒ 600s 的 **76%–99% 花在工具调用之间的模型推理**上（~9–25 s/回合 × 24–72 回合）。
「预算」实际约束的是**回合数 × 单回合延迟**，而不是工具执行。

### 2.4 形状：71/87 是「一直干到墙」，6 个是「停摆」

以「末次工具调用距 run 结束」分档（**基数 = 有任务行的 78 条**，见 §2.2）：

| 形状 | 条数 | 平均调用数 | 判读 |
| --- | --- | --- | --- |
| 干到墙（tail < 60s） | **71** | 54 | 登记描述的这一类：**一直在行动，被墙截断** |
| 停摆（tail ≥ 120s） | **6** | 19 | **另一回事**：最后一次调用之后再无动作 |
| tail 60–120s | 1 | 10 | 边界 |

停摆的最清晰一例是 `I1`：末次工具调用 `06:11:25`（`edit_file`），run 结束 `06:15:52`——
**267 秒内没有任何工具调用**，`workflow_events` 里这 267s 只有结束时落盘的 `TASK_FAILED` 与
`agent_artifact_created`。⇒ 这是**单次超长模型生成（或一次未被记录的挂起）**，不是「任务太大」。
**按 [[defect-registration-needs-code-proof]]：只有形状、没有机制 ⇒ 不登记**，留作 §11 备查。

### 2.5 决定性对照：**墙钟先于回合守卫触发**

这一条决定「抬墙钟有没有用」。若回合守卫先到，抬墙钟只是让运行改撞 `TOOL_ERROR`。

`AgentGraph.ts:229` 的平台守卫是 `state.iteration >= options.maxIterations`（50），报
`TOOL_ERROR: Agent reached max iterations`；`recursionLimitFor(50) = 104`（`AgentRunner.ts:82-84`）。

```sql
SELECT CASE WHEN error->>'code'='TIMEOUT_ERROR' THEN 'TIMEOUT_ERROR'
            WHEN error->>'message' LIKE '%max iterations%' THEN 'reached max iterations'
            ELSE coalesce(error->>'code','(no error)') END AS outcome, count(*), max(created_at)
FROM agent_runs WHERE created_at>='2026-10-01' GROUP BY 1;
```

| outcome | 条数 | 最晚一次 |
| --- | --- | --- |
| `TIMEOUT_ERROR` | **47** | **10-19 15:35** |
| `reached max iterations` | 14 | **10-17 14:55** |

⇒ **10-17 之后回合守卫一次都没触发，而超时一直在触发**。当前**墙钟是真正的约束**，
抬墙钟**确实能换到更多回合**（不是白改）。

### 2.6 致败点核实（查库，不采信 summary）

最近 4 个含 600s 超时的工作流：

| 工作流 | 结局 | 其中超时任务 | 其他失败 |
| --- | --- | --- | --- |
| `80a8a837`（L1-M4l） | **FAILED** | `T-02`、`T-02-DEBUG-1`（各 1 次） | `T-02-DEBUG-1-DEBUG-2`＝反篡改（N-14，**已修** PL-M21） |
| `2d1f1e78` | FAILED | `I1`、`I3-REPLAN-1` | `I2` / `I3` / `I3-REPLAN-1-REPLAN-2`＝`checks failed: test`（N-13 族） |
| `48cd16a5` | **SUCCESS** | `TASK-010` | 无（16 任务里唯一 1 个 FAILED） |
| `f45b6eb9` | **SUCCESS** | `T-007`、`T-008` | 另 1 个 FAILED |

⇒ 超时**确实是致败点**（`80a8a837` 的链正是被两个连续超时推到第三次尝试），但**不是唯一**，
且在两个工作流里没拦住链。**L1-M4l 的 9 个 FAILED 里 7 个是反篡改（已修）、2 个是超时**
⇒ 反篡改修掉之后，**超时成为该批剩余失败的最大份额**。这是本项该现在做、而不是押后的理由。

**顺带排除一处**：`T-02` 与 `T-02-DEBUG-1` 的超时读数完全相同（65 次调用 / iter 66），怀疑
「DEBUG 任务把源任务重做了一遍」。逐条比对工具调用集合：**只有 10/65 行相同** ⇒ **不成立**，未登记。

### 2.7 影响面：超时过的任务，约一半最终成功

```sql
WITH timed AS (SELECT DISTINCT task_id FROM agent_runs WHERE error->>'code'='TIMEOUT_ERROR')
SELECT t.status, count(*) FROM timed JOIN tasks t ON t.id=timed.task_id GROUP BY 1;
```

| 任务的最终状态 | 任务数 |
| --- | --- |
| SUCCESS | **28** |
| FAILED | 27 |
| READY | 3 |

且**重试那一次明显更快**（成功那次的 p50 多在 60–260s，最高 587s）——因为**工作区跨尝试保留**，
第一次尝试写下的产物还在，重试不必从零搭脚手架。
⇒ 现有「超时 → 重试」路径**已经能救回约一半**，本项买的不是「唯一出路」，是**第一次就做完**。

### 2.8 成本：抬 1.5× 的增量对批预算可忽略

按 run 时长分档的 token 用量（`status='succeeded'` 且 `token_usage` 有效）：

| 档 | 条数 | 平均输入 | 其中缓存 | 平均输出 |
| --- | --- | --- | --- | --- |
| < 120s | 1920 | 80,010 | 70,277 | 3,165 |
| 120–300s | 652 | 327,420 | 295,175 | 7,763 |
| 300–540s | 151 | 585,213 | 543,357 | 8,962 |
| **540s+（撞墙档）** | 13 | **667,006** | 610,314 | 11,847 |

抬到 900s ⇒ 仍撞墙的那些 run 多跑约 50% 回合 ⇒ 单次约 **+33 万输入 token**。
近期一批（L1-M4m）含超时任务约 3 个 ⇒ **约 +100 万 token / 批**，对 200M 的批守卫是 **0.5%**。
**且反向还有节省**：每避免一次「超时→重试」，省下整整一次尝试（重试约 40 万输入 token）。
⇒ **成本不构成反对理由。**

### 2.9 没有别的上限会接管

`WorkflowPolicy.maxWallClockMs` / `maxTokens` 是**可选**字段（`packages/shared/src/index.ts:847-849`），
只在工作流显式声明时生效。查库：**10-01 起 291 个工作流，声明 `max_wall_clock_ms` 的 0 个、
声明 `max_tokens` 的 0 个**。⇒ 抬任务预算**不会被工作流级预算截断**。

### 2.10 三个候选的取舍

| 候选 | 判定 |
| --- | --- |
| **抬预算** | **取**。墙钟是当前真正的约束（§2.5）；旋钮已存在且有测试；一行 + 一个断言；可逆、可度量。 |
| 按类型给不同窗口（`TASK_TIMEOUT_MS_BY_TYPE`） | **否**。撞墙的是 BACKEND / DATABASE / DEBUG / BUILD / TEST——**工作类型全都撞**；而 DESIGN（max 259s）/ ANALYSIS（234s）/ REVIEW（416s）/ FRONTEND（377s）**一次都没接近过 600s**。分档只是把同一个数字抄五遍，**零收益**。 |
| 拆任务（规划侧） | **否（本轮）**。它更接近根因（一个任务要 50+ 回合），但：① 爆炸半径在规划器，无库内证据支持；② **当前墙钟会截断观测**——我们**看不见**「本来会在 700s 做完」的那一段，所以**现在无法判断尾巴有多长**。先抬预算把尾巴量出来，再决定要不要拆。 |

**取值 900s（1.5×）的依据**：已知**成功**的 BACKEND run 最高 **642s**、近期撞墙的 6 个实例在
583–604s 时**仍在行动** ⇒ 600s 正好压在真实分布的长尾里；900s 是**最小**能盖住已知天花板
（642s）并留出余量的整数档。

## 11. Known Issues

1. **本项不判「已关闭」。** 关闭条件＝真实批次里「因撞墙而致败的任务」显著减少。**未验证前一律不勾选**
   （[[acceptance-under-claim]]）。
2. **这既是一次修复，也是一次测量。** 当前墙钟会**截断观测**：我们看不见「本来会在 700s 做完」的样本。
   抬到 900s 后若超时**只是平移到 900s**，那说明尾巴很长、任务本身就做不完 ⇒ **结论应升级为「拆任务」
   （规划侧）**，那是另一个、更大的改动，本文件不预支。
3. **新留备查 1 条（缺机制，未登记）**：**6/87 个超时 run 属于「停摆」**（末次工具调用后 ≥120s 无动作，
   最典型的 `I1` 空转 **267 秒**）。这与「干到墙」的 71 条**不是同一回事**，更像单次超长生成或未被记录的挂起。
   **只有形状、没有机制 ⇒ 按 [[defect-registration-needs-code-proof]] 不登记**；下一批复核时一并看。
4. **`maxIterations` 仍是硬编码的 50**（`workflowTaskExecutor.ts:302`）。本项只抬墙钟，**没有动它**。
   若抬墙钟后 `reached max iterations` 重新出现，说明回合守卫改成了先到的那一个——**那是新现象，须重新普查**。
5. **历史 `agent_runs` 一行未改**（`AGENTS.md` §6 红线）。修前落盘的 87 条超时记录是当时的观测记录，
   按 `docs/146` §6 规则 7 冻结，勘误只以追加块登记（本文件即该追加块）。
6. **本判定依赖当时的模型延迟与回合数分布**（~9–25 s/回合）。换模型、换 provider 或改 `maxIterations`
   都会移动这条线，**须重新普查，不能沿用本文件的取值依据**。
