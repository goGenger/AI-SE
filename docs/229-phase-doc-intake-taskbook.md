## 1. 为什么要有这个阶段（现状核实）

| 事项 | 现状（实查） | 证据 |
| --- | --- | --- |
| 建需求收什么 | **只有一个字符串**：`title` / `description` / `rawContent`，其中 `rawContent` **上限 20,000 字** | `packages/shared/src/index.ts:283-287` |
| 需求表有什么列 | `id / project_id / title / description / raw_content / status / version / created_at / updated_at / autonomy_level` | 库内 `requirements` |
| 前端入口 | 一个文本框，预填一段示例 PRD；无文件选择器 | `apps/web/src/views/RequirementsView.vue:107-109, 179-181` |
| 请求体上限 | **1 MB**（`express.json({ limit: "1mb" })`） | `apps/server/src/app.ts:76` |
| 有没有上传能力 | **没有**：全仓无 multipart 解析器、无静态上传目录，`apps/server` 的生产依赖里没有任何解析库 | `apps/server/package.json` 依赖清单 |
| 技术规格能不能由人给 | **不能**：`specifications`（FUNCTIONAL / TECHNICAL / ARCHITECTURE / API / DATABASE / UI）**只能由规划器生成**，`insertSpecification` 只在规划保存路径里被调用 | `packages/database/src/planningRepositories.ts:322, 873, 1005` |
| 规划怎么消费需求文本 | `rawContent` 原样进入规划图 | `packages/agent-core/src/planning/PlanningGraph.ts:262` |
| **AC 是怎么来的** | **从 `rawContent` 里按 Markdown 的 FR 标题与 AC 表格行解析** | `PlanningGraph.ts:387`、`planningService.ts:1059`、`acceptanceCriteria.ts:61-72` |

**结论**：现在的模型是「**一份 PRD 文本 → LLM 推导出全部技术规格与任务**」。真实工作里常见的两件事都无处安放：

1. **文件形态的 PRD**（Word / Markdown 文件）——只能靠人手工复制粘贴，且撞 2 万字上限；
2. **已写好的技术需求文档**（架构、接口、数据模型）——系统不但不能接收，**还会把它重新"推导"一遍**，等于用 LLM 的猜测覆盖团队已经定好的方案。

## 2. 本阶段的语义定义（用户已给出方向，这里是把它写死）

**用户口径**：上传的技术需求文档**一定是已经规划好的**，系统要**提取内容并据此规划**。

由此推出三条硬语义：

1. **技术文档是权威输入，不是参考材料。** 规划器发生成「技术规格」与「任务分解」时，必须以文档为基线；**与文档矛盾的产出视为缺陷**，而不是"另一种合理设计"。
2. **仍然要规划。** 权威不等于把文档当任务清单——切片划分、任务分解、依赖与 AC 映射仍由平台产出，只是**受文档约束**。
3. **冲突必须上报，不得静默择一。** 文档与 PRD 冲突时（例如 PRD 要求某接口、文档里没有），必须显式记录冲突项并交人工，不允许 LLM 自行取舍。

**由此也推出一条硬规则（实现层）**：技术文档**绝不拼进 `rawContent`**。因为 `rawContent` 是 AC/FR 解析器的唯一输入（§1 最后一行），拼进去会把文档里的编号、表格误当验收标准。

## 4. 任务明细

### M1 文档模型与存储

**D1-1 文档表**
- 新表 `requirement_documents`：`id uuid pk`、`requirement_id uuid fk`、`kind varchar(16)`（`PRD` / `TECHNICAL`）、`file_name varchar`、`mime_type varchar`、`byte_size int`、`sha256 varchar(64)`、`content_text text`、`raw_bytes bytea`、`created_at timestamptz`。
- 遵循仓库迁移纪律：`CREATE TABLE IF NOT EXISTS`、`gen_random_uuid()`、PG16；扩展 `migrate.test.ts` 的文件清单（16 → 17 → **18**）与 `at(-1)`。
- **为什么留 `raw_bytes`**：抽取规则将来会改（换解析器、修换行），届时只有留原件才能重放。docx 通常几百 KB，PG 无压力。
- **唯一性**：`(requirement_id, kind)` 对 `PRD` 唯一（最多一份），对 `TECHNICAL` **不唯一**（允许架构 / 接口 / 数据模型分开上传——见 §6 第 5 项）。

**D1-2 类型与仓储**
- `RequirementDocument` 与 `RequirementDocumentKind` 放 `packages/shared`（跨包契约，`AGENTS.md` §3）。
- 仓储方法：`create` / `findByRequirementId` / `findById` / `delete`。**不提供 update**——文档是快照，改就是重新上传。

### M2 上传与抽取

**D1-3 上传端点**
- `POST /api/requirements/:id/documents`，请求体为**原始字节**（`express.raw({ type: [...], limit })`），元数据走 query（`kind`、`filename`）。
- **为什么不用 multipart**：需要新增解析依赖，而单文件上传用 raw body 零依赖即可（浏览器 `fetch(url, { body: file })` 直接可行）。
- 校验顺序：需求存在 → `kind` 合法 → 扩展名与 MIME 在白名单 → 大小 → 抽取成功。任一失败返回 **4xx + 可读原因**，错误码复用既有封套，不新增错误码体系。

**D1-4 抽取器**
- `.md` / `.txt`：UTF-8 解码，去 BOM，统一换行。
- `.docx`：解压后取 `word/document.xml`，抽 `<w:t>` 文本，按段落合并。**实现方式见 §6 第 3 项。**
- 抽取结果为空或全是空白 → 拒绝（"文件里没有可读文本"），不落库。
- 正文超过上限（默认 **200,000 字符**）→ **截断并在返回体里明确告知截断位置**，不静默丢。

**D1-5 PRD 走文件的情形**
- 上传 `kind=PRD` 的文件时，抽取文本**写进 `requirements.raw_content`**（这是 AC 解析器的唯一输入，§2），同时落一条文档行保留原件。
- `rawContent` 的 2 万字上限**在本阶段放宽到 200,000**（否则文件 PRD 仍然装不下）；放宽只改 schema 常数与前端提示，不改解析器。

### M3 规划接入

**D1-6 技术文档进入规划**
- 规划输入新增 `providedTechnicalDocs: Array<{ fileName, text, truncated }>`，与 `rawContent` **并列**、绝不合并。
- 提示词明确：**「以下技术文档由用户提供，已是既定方案；你的技术规格与任务分解必须与之保持一致。发现与 PRD 的冲突时，写入 `conflicts` 而不是自行取舍。」**
- 计划中的技术规格（TECHNICAL / ARCHITECTURE / API / DATABASE）**以文档为基线**：模型可以补全文档没写的细节，但**不得改写文档已写明的**。

**D1-7 冲突上报**
- 规划结果新增 `conflicts: Array<{ topic, prdSays, docSays, source }>`；非空时**写一条事件**并在需求详情页显性展示。
- 冲突**不阻塞**规划（否则一个措辞差异就能卡住整条链），但会进入人工可见面。

**D1-8 已分析后再加文档**
- 需求已有规划结果时上传文档 → 标记「规划已过期」，前端在「分析」按钮旁显性提示，**要求重新分析**才继续。
- 不允许静默沿用旧规划（否则文档形同虚设）。

### M4 前端入口

- 新建需求弹窗：`PRD` 区域支持「粘贴文本」与「选择文件」两种方式（文件走 M2 的端点；创建后立即上传）。
- 需求详情页新增「技术文档」分区：列表（文件名 / 类型 / 大小 / 抽取字数 / 是否截断）、上传、删除、以及 `conflicts` 展示。
- 所有新增展示逻辑放 `viewmodels/`（`AGENTS.md` §5），`.vue` 不堆可测逻辑。

### M5 验证

| 层 | 内容 |
| --- | --- |
| 单元 | 抽取器三格式正/反例（空文件、坏 docx、超长截断）；AC 解析器**未被技术文档污染**的反向对照 |
| 集成 | 真 PG：文档落库、唯一约束、删除、PRD 替换 |
| E2E | 上传 → 抽取 → 规划（假模型）全链；冲突上报；规划过期标记 |
| 回放 | 用一份真实技术文档跑一次规划，人工核对产出是否引用文档内容（不烧配额优先用假模型） |

## 8. 红线

- **不新增第二套错误码 / 审批 / 审计体系**；上传失败走既有错误封套。
- **技术文档不进 `rawContent`**（`AGENTS.md` §10 的"唯一来源"精神；也是 D1-3 的断言对象）。
- 明文凭据不落文档表；`content_text` 入库前走 `@ai-se/observability` 的既有 sanitize。
- 不修改任何 `dist/`；不做运行期重启实验。
- 上传是**写操作**，必须带既有的鉴权与请求日志，并与其它写接口同一套错误映射。
